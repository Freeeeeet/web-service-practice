# Пульс — Uptime & Ping

Учебный проект по Docker Compose, **вариант 11**: проверка доступности указанного веб-сайта и хранение журнала проверок в PostgreSQL.

## Запуск

Нужны Docker Engine / Docker Desktop (на macOS также подходит Colima) и Docker Compose v2 или новее. Локальные Node.js и PostgreSQL для запуска не нужны.

```bash
git clone git@github.com:Freeeeeet/web-service-practice.git
cd web-service-practice
docker compose up -d --build --wait
```

Откройте **http://localhost:8080**. Первая сборка требует интернет для скачивания образов и npm-зависимости `pg`. После сборки демо-сценарии работают без интернета. Для проверки настоящих сайтов интернет нужен контейнеру `web-service`.

Настройки необязательны: значения для локального учебного окружения уже заданы в Compose. Чтобы изменить порт или параметры БД:

```bash
cp .env.example .env
# Отредактируйте .env перед первым запуском.
docker compose up -d --build --wait
```

`FRONTEND_PORT=8081` меняет адрес интерфейса на http://localhost:8081. Файл `.env` не попадает в Git. Пароль по умолчанию — только для локальной практики. Изменение переменных PostgreSQL не меняет пользователя/пароль уже инициализированного тома.

## Что показать на сдаче

1. `docker compose ps` — работают **4 контейнера**, у каждого есть healthcheck.
2. Нажмите **«Загрузить журнал»**: данные читаются из PostgreSQL через бэкенд.
3. Введите `https://example.com` и нажмите **«Проверить сайт»**: бэкенд обращается к отдельному веб-сервису, получает HTTP-код и время ответа, затем сохраняет запись.
4. Кнопки **«Доступен»**, **«Ошибка 503»**, **«Тайм-аут»** запускают настоящие запросы к встроенным демо-страницам. Записи явно отмечены «ДЕМО»; тайм-аут занимает около 8 секунд.
5. Выберите фильтр «Доступны» или «Недоступны» — запрос фильтруется в БД.
6. Перезапустите контейнеры, обновите журнал: история сохранится в именованном томе.

Начальная БД содержит три **синтетические демо-записи**, чтобы журнал не был пустым. Они не выдаются за реальные измерения. Статистика включает все сохранённые записи, в том числе демо.

## Архитектура

```text
Браузер → localhost:8080
             │
        frontend (Nginx)
             │ /api/*
        backend (Node.js REST API)
             ├── db (PostgreSQL 16) → том postgres_data
             └── web-service (Node.js) → проверяемый HTTP/HTTPS сайт
```

| Контейнер | Назначение | Внутренний порт |
| --- | --- | --- |
| `frontend` | HTML/CSS/JS, Nginx, проксирование API | 80 |
| `backend` | REST API, чтение и запись журнала, вызов сервиса проверки | 3000 |
| `db` | PostgreSQL, автозаполнение из `db/init.sql` | 5432 |
| `web-service` | HTTP-проверка доступности, время ответа, обработка ошибок | 4000 |

Compose создаёт общую bridge-сеть; сервисы обращаются друг к другу по именам. На хост опубликован только фронт, на `127.0.0.1`. Бэкенд ждёт готовности БД и сервиса проверки, фронт — готовности бэкенда. Браузер использует API с того же origin, отдельная настройка CORS не нужна.

## Как определяется доступность

- Проверка — HTTP GET до получения заголовков ответа; тело страницы не скачивается. Это **не ICMP ping** и не фоновый мониторинг.
- HTTP 200–399 → «Доступен». HTTP 400–599, DNS/TLS/сетевые ошибки и тайм-аут → «Недоступен».
- Время включает DNS, соединение, TLS и получение заголовков, а также перенаправления. Это разовое наблюдение из контейнера, а не процент uptime за период.
- Общий тайм-аут 8 секунд; не более 3 перенаправлений, 5 одновременных проверок. Антибот-защита сайта может вернуть 403 даже при доступности сайта в браузере.
- Поддерживаются сайты с IPv4 и стандартными портами 80/443. IPv6-only сайты не поддерживаются.
- Приватные/служебные адреса, URL с паролями и произвольные порты запрещены. DNS-адрес проверяется и закрепляется на время подключения; адреса перенаправлений проверяются заново. Исключение — три фиксированные локальные демо-страницы.
- Ошибка самого сервиса проверки не записывается как недоступность сайта: API возвращает ошибку пользователю.
- Журнал показывает последние 100 записей по фильтру; счётчики охватывают всю таблицу. Время в интерфейсе — часовой пояс браузера, в БД — `TIMESTAMPTZ`.

## REST API

| Метод | Путь | Результат |
| --- | --- | --- |
| GET | `/api/health` | Готовность БД и сервиса проверки |
| GET | `/api/checks` | Последние 100 проверок и общая статистика |
| GET | `/api/checks?status=up` | Только доступные; `down` — только недоступные |
| POST | `/api/checks` | Проверить URL, сохранить результат, вернуть запись (201) |

Тело POST: `{"url":"https://example.com"}`, заголовок `Content-Type: application/json`.

Веб-сервис доступен только внутри сети: `GET /health`, `POST /check` и демо-страницы `/demo/ok`, `/demo/error`, `/demo/slow`.

## Проверки проекта

Модульные тесты не требуют установки npm-пакетов: в тестируемых модулях используются стандартные API Node.js. При установленном Node.js 24+:

```bash
node --test backend/test/*.test.js web-service/test/*.test.js
```

После запуска Compose интеграционная проверка использует **существующий** контейнер бэкенда и проходит через Nginx, API, веб-сервис и реальную БД:

```bash
docker compose exec -T backend node --input-type=module < tests/smoke.mjs
```

Она проверяет HTTP 200/503, тайм-аут, отклонение приватных URL, сохранение и фильтрацию. Добавляет три помеченные демо-записи. Проверка сохранности при пересоздании:

```bash
docker compose down
docker compose up -d --wait
# Обновите журнал — записи остались.
```

## Полезные команды

```bash
docker compose ps                       # состояние контейнеров
docker compose logs --tail=100           # последние логи
docker compose logs -f backend web-service
docker compose stop                     # остановить, сохранив контейнеры и данные
docker compose start                    # снова запустить
docker compose down                     # удалить контейнеры и сеть, сохранить данные
```

**Сброс всех данных:** `docker compose down -v` удалит том с журналом. Следующий запуск заново выполнит `db/init.sql`. Скрипты в `docker-entrypoint-initdb.d` выполняются только при первом запуске пустого тома.

## Состав репозитория

```text
docker-compose.yml     # ровно четыре сервиса, сеть, healthchecks, volume
.env.example           # необязательные настройки
frontend/              # интерфейс, Nginx и Dockerfile
backend/               # REST API, драйвер pg, Dockerfile и тесты
web-service/           # отдельный сервис проверки, Dockerfile и тесты
db/init.sql            # схема и начальные демо-данные
tests/smoke.mjs         # интеграционная проверка работающего Compose
```

Публикация исходников в GitHub и внесение ссылки в таблицу группы выполняются отдельно.
